# Foldnex product contract

<!-- impeccable:product-schema 1 -->

## Platform

Version 2.0.0 is a Chrome extension using Manifest V3, with no transpilation step and no runtime package dependencies. `manifest.json` declares Chrome 120 as the minimum browser version; that does not guarantee Gemini Nano eligibility. The module service worker is `background.js`, the popup is `popup.html`, and Settings opens `options/options.html` in a tab.

The extension requests `tabs`, `tabGroups`, and `storage`, plus the seven HTTPS provider hosts and `http://localhost:11434/*`. It has no content scripts or browser-history permission. The `tabs` permission exposes tab metadata, and host access permits configured provider requests; neither means page bodies are inspected.

## Users

Chrome users with crowded windows who want to restore a usable tab strip without manually finding duplicates or sorting every page.

## Product purpose

One action should leave the current window visibly cleaner: a single sensible copy of each ordinary web page and a small number of task-oriented Chrome tab groups.

## Positioning

Foldnex is a practical tab-organisation utility, not an AI showcase. It combines conservative duplicate removal, exact semantic result reuse, explicit user rules, optional AI labelling with local planning, and an offline fallback.

## Primary surfaces

- **Popup:** tab count, cleanup action, ungroup action, a first-run setup card until an engine choice is saved, grouping strategy, active task engine, local-memory summary, and direct-toolbar preference.
- **Options:** three sections, **Grouping engines**, **Rules & memory**, and **Behaviour**. Engines uses a reversible compact chooser, one vertical provider list, and shared configuration panels with model catalogs and connection tests. Rules manages explicit URL rules and grouping memory. Behaviour includes strategy, toolbar mode, Auto-group, collapse preferences, last-cleanup diagnostics and separate provider-request totals.
- **Toolbar and commands:** progress/result badge plus group and ungroup keyboard shortcuts.

## First-run setup

- The popup shows a setup card below the cleanup action until `setupChoice` (`cloud`, `nano` or `offline`) is saved in sync storage. New installs and earlier installs without that preference see it the next time the popup opens; with **Run from toolbar** on, the toolbar icon keeps opening the popup until `setupChoice` is saved and only then runs cleanups directly. Automatic warming does not start before that choice. The card never blocks or disables **Clean up and group**, which can attempt the saved engine immediately. The saved engine is marked Current: an earlier version's choice, or on a new install the Gemini Nano default that the service worker saves at install.
- **Cloud AI** selects the first cloud engine with a saved credential: the current engine, then OpenAI, then the rest in catalog order. It checks only that a credential exists in local storage and never shows it. Without one it saves only `setupChoice` and opens Settings at `#engine`, reusing an open Settings tab. Settings then previews OpenAI with its key field focused and says that the saved engine stays in use; saving a key for the previewed cloud engine selects it.
- **On this device — Gemini Nano** selects Gemini Nano and turns on background preparation. The choice is disabled with Chrome's reason when the Prompt API reports the model unavailable. When Chrome still needs to download the model, the choice is saved and Settings opens so the download can start.
- **Offline — no AI** selects Offline smart mode.
- When Ollama is the saved engine, a fourth choice, **Keep Ollama**, leaves the engine and background preparation unchanged and saves `nano` for Ollama on a loopback address, otherwise `cloud`. For Ollama at another address its copy says that page titles and a short site hint are sent to that server.
- The card's copy states the on-device memory cost (about 3 GB while the model is loaded), the current unload setting, and the 15-25 second first load, and says that the Cloud choice sends page titles and a short site hint to the provider.

## Core workflow

1. Resolve the active Chrome window and its incognito boundary.
2. Remove duplicate ordinary web pages and allowlisted stateless Chrome pages using a conservative canonical URL.
3. Exclude pinned and browser-internal tabs from grouping.
4. If By site category is selected, classify locally from the address using the stable service taxonomy and site-name fallback.
5. Otherwise lock explicit user-authored URL rules first, then Socials, and reuse a cached result only when the complete semantic fingerprint set is unchanged. Every other tab needs one category label from a fixed vocabulary of 23 keys. Labels come from the per-tab label cache (keyed by a title and URL fingerprint plus engine, requested model, effective effort, endpoint identity and prompt/vocabulary revision, kept seven days) or from the selected engine within a 4.5-second click budget, reserving 600 ms for application. Nano labels batches sized to its stored speed estimate, up to 20 tabs; cloud engines receive one request up to 40 tabs, then parallel batches of 25. Offline smart mode uses local inference and skips model labels. The local planner validates model output and decides the final membership and group count; Chrome APIs create the groups.
6. Tabs the engine could not label before the deadline are placed provisionally from their site, a labelled neighbour on the same site, or title words. Provisional tabs are reported and never cached. An on-device engine labels them in the background right after the cleanup, even with background preparation and Auto-group off. With a cloud engine, a batch that answers after the deadline is cached for the next cleanup, and the background retries only tabs that **Auto-group new tabs** covers.
7. The local planner turns labels into coherent groups within the ten-group maximum, using a smaller-window count as a preferred target, assigns every tab exactly once, and names groups deterministically. Remembered names apply first (user renames, then earlier model names). When fewer than half of the groups have a remembered name and time remains, Nano may name them in one prompt, or a cloud engine or Ollama may consolidate the candidate groups into named folders. With **Cloud economy mode** on, the optional cloud naming/consolidation path is skipped; remembered and deterministic names remain, and on-device naming is unchanged. A prepared window, whose labels all came from the cache, waits at most `PREPARED_NAMING_WAIT_MS` (1.2 seconds) for that answer; other windows wait while the budget allows. A late answer is remembered for the next cleanup and never regroups the strip.
8. Apply exact scoped rename preferences, then coherent count enforcement once more as a safety net.
9. Create groups in their existing left-to-right order and report privacy-safe diagnostics.

The budget bounds waiting for model work; Chrome API calls and storage operations can extend total wall time. Duplicate removal still runs when fewer than two unpinned groupable tabs remain, but no groups are created. A live-tab read before application excludes tabs that have vanished or become pinned, with a retry when Chrome reports a tab-state change. This reduces races without making the entire cleanup an atomic browser operation.

## Background classification

- Background work is opt-in. It runs only under the consent rules below and while **Prepare groups in the background** (`backgroundPrep` in sync storage, off when unset) or **Auto-group new tabs** is on. The one exception is a cleanup's follow-up: with an on-device engine, the tabs a cleanup placed by address are queued with reason `cleanup` (the `cleanupFollowUp` scope) and labelled even with both off, with no plan refresh or naming, and then background work stops. The queue checks this before each labelling batch and each plan refresh; the service worker checks it before queueing open tabs, handing over a cleanup's provisional tabs, and moving the popup's window to the front.
- When a tab finishes loading, the service worker queues it and labels it after a short delay, storing each batch as it lands, so a later cleanup only applies cached labels. A busy queue still flushes within about 5 seconds of its first tab. Discarded and not-yet-loaded tabs are labelled from their saved title; a tab that is still loading waits for its load.
- With an on-device engine, the tabs a cleanup placed provisionally are queued the same way, even with background preparation and Auto-group off. The popup explains that background labels prepare a later cleanup; this follow-up does not immediately regroup those tabs. While background work is allowed, so is every open tab in every non-incognito window after a browser start, after an extension install or update, and once when background preparation or Auto-group is turned on. With a cloud engine, provisional tabs that Auto-group does not cover wait for another cleanup attempt, and the popup says so.
- Changes to the engine, endpoint, model, reasoning, credentials, consent or reset generation stop the running background batch and drop queued tabs, pending retries, plan refreshes and older fresh-page admissions. Outstanding local window reads cannot refill the queue under the new configuration. Explicit choices to keep a tab ungrouped remain in effect until its next navigation.
- A title-only change, or an address change within the same page (a fragment, or a map or app rewriting its address), re-labels a tab at most once every 10 minutes until the tab opens a new page. A tab that comes back unlabelled is retried after 5 seconds, 30 seconds and 2 minutes; after four failed attempts it waits until it opens a new page, and a cleanup that places it provisionally, or with an on-device engine opening the popup, tries it once more.
- A few seconds after a window's last new label, the service worker refreshes that window's plan, postponing it by at most about 15 seconds. With an on-device engine it may name the plan's groups, Nano by naming and loopback Ollama by consolidation (at most once per window every 30 seconds, and only when the plan changed), so the next cleanup needs no model call.
- Opening the popup warms Nano when it is the selected engine for By task and `setupChoice` is saved, unless the unload setting is `immediately`, which would release the model 6 seconds after its load. Automatic warming requires an answered setup card; a requested cleanup can still start a model load before that choice. While background work is allowed, opening the popup also moves the current window's tabs to the front of the queue for an on-device engine. A browser start, an install or update, and a service-worker start warm Nano only while background preparation or Auto-group is on.
- Chrome Gemini Nano and Ollama on a loopback address (`localhost`, `127.0.0.1` or `[::1]`) need no cloud consent because tab data stays on the device. Beyond a cleanup's follow-up, they label in the background only after the user turns on background preparation, in Settings or by choosing Gemini Nano in the setup card, or turns on Auto-group. Auto-group needs labels, so while it is on with an on-device engine, background preparation stays active and Settings says so. Ollama at any other address counts as a cloud engine.
- Cloud engines label in the background only when the user turns on **Auto-group new tabs**, and then only tabs opened or sent to a new page after it was turned on, as its setting states. Background preparation never enables cloud background labelling. Tabs that were already open, title or in-page address changes after a page's first 10 seconds, popup opens and browser starts send nothing. Background cloud batches are sent one at a time, and background runs never make cloud consolidation requests.
- With **Auto-group new tabs** on, a tab opened or sent to a new page while the setting is on is filed as it loads. Tabs Chrome restores in the first 20 seconds after it starts, or restores without loading, are not new. The tab joins the Chrome group that already holds most of its planned group's tabs, or a group with the same name when none of them is grouped. A new group forms only when no tab of that planned group is grouped yet (Review Later aside), two such tabs share it, and the window still has fewer than ten titled groups.
- A tab the user takes out of a group, or that **Ungroup current window** (or its shortcut) ungroups, stays out until it opens a new page; an address change within the same page does not count. Only a new tab's own load starts an auto-group; opening the popup, a cleanup, and other tabs' reloads or title changes never do. Explicit URL rules and Socials take precedence, Review Later is never auto-created, and grouped tabs are never moved. A cleanup or an ungroup cancels an auto-group in progress before its next change; a group it has just created still gets its name.
- Incognito tabs are never classified in the background.

## On-device model memory

- While Foldnex holds a Gemini Nano base session, Chrome keeps the model loaded. In a measured test on an Apple Silicon Mac, that took about 3 GB of memory, and a cold load took 15-25 seconds.
- `modelUnloadAfter` in sync storage (`immediately`, `2m`, `5m`, `15m`, `60m` or `never`; `5m` when unset or unrecognised) sets how long Foldnex holds an idle model. Creating or reusing a base, a warm, and a prompt each restart the idle clock. A load, a prompt, or a whole labelling run in progress holds the model against idle unloading. One timer, re-armed from the last use, releases the base sessions once the model has been idle longer than the setting. `immediately` waits a 6-second grace so a naming prompt right after labelling, in a cleanup or in the background plan refresh about 4 seconds after the last label, does not reload the model. `never` holds it only while Chrome keeps the service worker running. A changed setting applies at once, so a model already idle long enough is released straight away.
- Once Foldnex lets go, Chrome frees the memory itself; in the same test that took about 5 minutes after the last use. Labels stay cached, so only unlabelled tabs need the model loaded again.
- Switching the engine away from Gemini Nano releases the sessions. The service worker first pauses background work for up to 1 second, so a running batch cannot load the model straight back.
- For Gemini Nano, Settings shows **Background work and memory**: the background preparation switch, the unload setting, a model-state line refreshed at most every 5 seconds while the engine page is visible, and **Free memory now**. For Ollama on a loopback address it shows only the switch. The service worker answers `GET_ON_DEVICE_MODEL_STATE` with `{ ok, loaded, idleMs, unloadAfter }`, where `idleMs` is 0 while the model is in use and `null` when it is not loaded. It answers `UNLOAD_ON_DEVICE_MODEL` with `{ ok, released }`. Manual release clears the held base sessions after pausing background work for up to 1 second; a prompt already running can finish on its own clone, and a pending base is destroyed when its load settles. If background preparation still has tabs queued, the next batch can load the model again.
- Requests to Ollama on a loopback address carry the same setting as Ollama's `keep_alive`: `0` for `immediately`, the same duration string from `2m` to `60m`, and `-1` for `never`. Actual unloading depends on the server's support for that field on its OpenAI-compatible endpoint. When honoured, `0` unloads after every request, so each background batch can reload the model. Ollama at another address and cloud providers never receive it. The Nano model-state display and **Free memory now** do not inspect or unload an Ollama server.

## Duplicate-survivor contract

- Ignore ordinary document anchors but preserve route-like fragments.
- Keep HTTP and HTTPS identities distinct.
- Retain query keys, values, order, host, port, and path.
- Prefer a pinned survivor, then the active tab, then the leftmost copy. A redundant pinned copy can close when the survivor is still pinned.
- Recheck both survivor and candidate immediately before removal.
- Deduplicate exact URLs for a short allowlist of stateless Chrome pages; preserve other non-HTTP(S) pages.

## Grouping contract

- **By task** uses each title, capped at 160 characters in prompts, as the primary semantic signal and its sanitised URL as supporting context.
- **By task** groups by active task or purpose, not simply by domain or media type. A title word shared across several categories and sites (for example a trip or a product) becomes its own task group.
- **By site category** uses only the address and makes no model request. Known services use a maintained service taxonomy. X, Reddit, and Slack are Socials; Gmail and Outlook are Email; assistants such as ChatGPT and Grok are AI · Assistants; AI provider consoles and documentation are AI · Platforms. AI groups never merge into Code, Cloud, or generic technology groups.
- In either strategy, known social services are kept in Socials rather than accepted inside system or administration groups. Explicit user-authored URL overrides still take precedence.
- By site category keeps every page under the same recognised base site together, including separate Envato account, asset, and content areas.
- YouTube, Envato, and Tesla are atomic dedicated groups. A multi-service category exceeding 15 tabs splits deterministically at service boundaries with namespaced labels such as Socials · X and AI · ChatGPT.
- Repeated unknown sites use a readable site name. One-off unknowns enter Review Later groups capped at eight tabs rather than producing one group per tab or one unbounded catch-all.
- Produce concise names and only Chrome-supported colours.
- Assign every current groupable tab exactly once.
- In By task mode, `groupCeiling(n)` in `src/ai-engine.js` is a preferred compactness target: 1 group for 2-3 tabs, 2 for 4-5, 3 for 6-7, 4 for 8-12, 5 for 13-17, 6 for 18-24, 7 for 25-31, 8 for 32-40, 9 for 41-49 and 10 from 50 tabs. Distinct topics may exceed the target, up to the absolute maximum of ten, when no coherent merge exists. A less varied window gets fewer groups; there is no minimum.
- In By task mode, `minGroupSize(n)` (2 up to 12 tabs, 3 up to 40, then 4) is a preferred size. Smaller groups may join a strongly related category; unrelated singletons stay separate. Above the preferred target, merges require affinity across constituent categories, including cached advice and model consolidation. Mixed category names describe both subjects rather than hiding a minority under the larger category. If the absolute limit requires reducing unrelated groups, a neutral Review Later group holds the overflow.
- Explicit rule groups and Socials retain their membership. If they alone reach ten groups, remaining tabs share one extra group and the planner flags `rules_exceed_ceiling`. Final compaction also preserves groups with a remembered user rename; protected groups can exceed ten, with any unprotected remainder placed together in Review Later.
- In By task mode, names are never Other or another vague catch-all. Model and remembered names are validated locally (at most 30 characters and 4 words, not generic, not made only of vague words such as Online or Services, free of decorative words such as Delights, not a bare domain, unique, not contradicted by a member's country-code domain, and not a single category name that conceals other constituent categories); a rejected name keeps the deterministic name. A user's own rename is kept as typed: control characters removed, cut to 30 characters at a word boundary, and refused only when it is empty, 'Review Later', or already used by another group in the window. No second model request is ever made to repair a result.
- In By task mode, oversized category groups split at a shared title word or site while there is room below the absolute ten-group maximum, including above the preferred target. An intact shared task or atomic service keeps its membership. Prospective merges exceeding the size cap are rejected in local planning, cached advice, provider consolidation and final compaction; consolidation receives the split candidates so it cannot restore an unsplit parent. Groups above roughly 28% of ordinary windows or 20% above 80 tabs (minimum cap eight) are flagged as a diagnostic. By site category deliberately permits large same-site groups.
- In By task mode, tabs that neither a label nor local inference can place (after the deadline, or in Offline smart mode) stay in one grey Review Later group, even when only one tab remains. Shared meaningful title evidence may attach an unlabelled tab to a task; lack of evidence never scatters it into another topic. Review Later is never merged into a real group.
- Preserve natural tab order inside groups and group order across the strip.

## Engine strategy

- Local options are Chrome Gemini Nano and offline smart mode.
- Cloud options are Google Gemini, OpenAI, xAI Grok, Groq, OpenRouter, DeepSeek, and Cerebras.
- Ollama defaults to the loopback endpoint at `http://localhost:11434/v1`, and compatible engines honour their saved base URL. Ollama at a non-loopback address is treated as cloud for background consent and economy mode. A saved endpoint grants no additional host permission: requests are subject to the manifest's seven HTTPS provider hosts, `http://localhost:11434/*`, and Chrome's network rules.
- By site category is a deterministic local strategy independent of the selected task engine and consumes no provider tokens.
- Site-category grouping does not request browser-history permission. The generic public taxonomy is maintained in source; personal mappings remain explicit local rules.
- Provider model catalogs are discovered live and presented in a native dropdown with a Custom model option. A catalog is an account-visible model listing, not proof that every listed model supports Foldnex's request format; OpenAI Responses-only Pro models are rejected before a Chat Completions call. Catalogs remain in the open settings page rather than a provider-only persistent cache. Committing a credential or endpoint change fetches a fresh catalog, and Test connection sits beside the key field and refreshes the catalog after a successful synthetic grouping request. A refresh preserves the selected model. Provider, credential, endpoint and request-generation checks prevent a stale response from replacing a newer catalog or reporting success for a different configuration. A synthetic connection test is an inference request that may incur provider charges and contributes to provider usage; it does not exercise ordinary tab grouping.
- Settings exposes reasoning effort beside supported models, with Low as the existing default. Label and consolidation requests use the saved effort; cached model labels are scoped to the provider, model, effective effort, endpoint and semantic revision. Available levels follow the selected provider and model; unsupported engines show no adjustable level. The popup shows the effective choice, and last-run diagnostics show the effort and any reasoning-token count reported by the provider. Requests use the provider's native parameter shape and omit incompatible sampling controls. Connection tests and grouping use the same rules.
- The OpenAI catalog entry uses `gpt-6-luna` at Low reasoning effort as its source default. **Priority processing** (`openaiPriority` in sync storage, on unless set to `false`) sends `service_tier: "priority"`; off explicitly sends `service_tier: "default"`. The connection test uses the currently displayed checkbox value. The provider decides its returned tier, availability and billing. Source defaults are not a current model-availability or performance guarantee.
- **Cloud economy mode** (`cloudEconomyMode` in sync storage, `false` when unset) is opt-in and preserves the existing refinement path by default. When enabled with a cloud engine, including remote Ollama, it skips optional cloud naming/consolidation without skipping needed category labels or local planning. Remembered or deterministic names remain. It neither changes on-device naming nor enables background cloud work. Exact-result cache scope includes the mode so an earlier result cannot bypass the selected behavior.
- Gemini requests set `generationConfig.maxOutputTokens` using the effort-based output-budget helper. Label and consolidation base budgets range from 768 to 1,536 tokens; supported Medium and High efforts raise the answer ceiling to 2,304 and 3,072. The shared helper allows 8,192 for providers and models supporting Xhigh or Max. Gemini 2.5 adds its explicitly configured thinking budget (512, 8,192 or 24,576 tokens) to preserve room for the JSON answer. The total cap includes hidden reasoning as well as the answer; it limits generated tokens, rather than guaranteeing a particular charge or a complete response.
- Non-incognito cloud label calls with matching fingerprints share only work already in flight under the same provider, endpoint, credentials, model, reasoning, Priority and reset-generation settings. Identical consolidation input and limits share an active request under the same settings. Sharing is worker-local and temporary; the identity and tab inputs are not persisted or logged. Callers receiving shared work add no second provider call or second token total. Incognito calls bypass sharing and usage recording.
- The Groq catalog entry uses `qwen/qwen3.8-27b` as its default model. This is a source default, not a current availability or comparative-quality guarantee.
- OpenAI label requests use a strict JSON schema whose values are the fixed category keys when the model supports Structured Outputs and the default OpenAI base URL is used; other OpenAI models use JSON-object output. Consolidation requests follow the same rule, and a request whose schema is rejected is retried once in JSON-object mode. Groq and the other compatible providers use JSON-object output, which avoids strict-schema `failed_generation` errors that can otherwise turn a recoverable answer into an HTTP 400. Every answer gets local ID and category validation. Nano uses a fixed-key schema with no arrays.

## Data and privacy contract

- API keys and bearer tokens live in `chrome.storage.local`, restricted to trusted extension contexts. The shared settings loader moves legacy Sync secrets to local storage before removing their Sync copies, preserves existing local values including explicitly empty credentials, and serializes migration with provider-secret saves. Other local data is not overlaid as settings, and non-secret Sync fields are not migrated.
- Non-secret engine preferences may sync through Chrome, including `setupChoice`, `backgroundPrep`, `modelUnloadAfter`, `cloudEconomyMode` and `openaiPriority`; these preferences hold no tab data.
- Cloud By task grouping sends titles (up to 160 characters each) and URL host/path hints to the selected provider; URL credentials, query strings, and fragments are removed first. Titles and paths can still contain sensitive information. Consolidation sends at most three member titles per candidate group, shortened to 60 characters, with its category key and tab count. With **Auto-group new tabs** on, the same title and hint of each tab opened or sent to a new page afterwards are sent in the background.
- Local storage keeps per-tab category labels (category key, engine ID, and time under a title and URL fingerprint; seven-day reuse eligibility, at most 3,000 entries) and group-name memory (category or hashed keys, title-word hashes, names, colours, and for user renames tab fingerprints; user renames eligible for 90 days, model names and merge advice for 14 days, at most 120 names and 200 cloud merge-advice pairs). Exact results contain fingerprints, group names, colours and planning metadata, with six-hour reuse eligibility and at most 12 results. Expired cache entries are excluded from reuse and removed during later writes, rather than by a guaranteed expiry-time deletion. Separate exact-cohort rename preferences retain fingerprints, names, colours and update times, capped at 100 entries without age expiry. These caches do not store raw titles or URLs, although group names can reflect tab content. Explicit URL rules separately store readable patterns and categories. A reset counter stops writes already in flight from restoring cleared grouping data, and the Nano speed estimate holds two timings. Each window's latest plan (tab IDs, names, colours, and category or hashed keys) lives in session storage only, as does Auto-group's list of tab IDs opened since it was turned on and an address hash for each tab taken out of a group.
- Unpacked development installs keep the latest phase-timing trace of a cleanup and of background work (phase names, timings, counts, window IDs, and the engine and strategy used) in local storage. Store installs and incognito runs never record one.
- By site category, offline smart mode, and a working Chrome on-device model do not make a cloud grouping request. Background preparation applies only to on-device engines and never sends tab data to a cloud provider.
- The setup card's Cloud choice reads local storage only to see whether a credential exists for a cloud engine; that check never displays, syncs or sends the credential.
- Page bodies are never read; there are no content scripts.
- Incognito grouping does not read or write rules, exact results, labels, name memory, window plans, the Nano speed estimate, diagnostics, provider-usage aggregates, session group-title baselines or group-rename preferences. The group-title listener resolves member tabs before retaining a baseline or learning a rename, because Chrome's group object does not reliably report incognito. User changes to shared settings can still persist. If a cloud engine is selected, its normal title and host/path transmission still applies.
- Programmatic group updates are marked in shared session storage and cannot become user corrections.
- Imported rule files are limited to 1 MiB and schema-validated before storage; the import path stops when the merged rule map reaches its 300-rule limit. Manual rule creation does not currently enforce that cap. Rule patterns are limited to 200 characters and use a bounded case-insensitive literal-segment matcher: `*` is the only wildcard and other punctuation is literal. Invalid, whitespace-containing or control-character patterns are rejected. Rule export includes patterns, categories, colours and rule metadata, without credentials or model-memory caches. Legacy pre-v2 rules are quarantined in a local backup instead of becoming active v2 rules automatically.

Semantic fingerprints normalise whitespace and control characters in titles and keep up to 1,000 title characters. They retain the complete HTTP(S) URL path and allowlisted semantic query parameters, while removing credentials, other query parameters and all fragments. Changes in ignored URL state do not invalidate an exact result or a per-tab label; these fingerprints are distinct from duplicate identity, which preserves all query values and route-like fragments.

Model labels, names and consolidation advice are scoped to the selected engine, requested model, effective effort, endpoint identity and semantic revision. A switch reassesses tabs once; returning to an earlier configuration reuses its entries within their TTL. Legacy unscoped model memory is not reused by scoped runtime calls. User-authored renames remain global. Model advice expires after 14 days and is bounded to 200 pairs across at most 12 scopes. Credentials, processing priority and economy mode are excluded from label identity; economy mode still separates exact results. Membership-planning revisions invalidate exact results separately from per-tab labels, allowing corrected plans to reuse existing classifications.

The popup labels saved cloud credentials as configured rather than ready, and shows safe failure guidance for a matching provider/model cleanup. Nano availability means downloaded, while the model-memory panel reports loading and loaded state separately. Provider HTTP bodies are never shown as model-catalog or connection-test errors.

## Provider usage and clearing

- **Last cleanup** retains execution diagnostics and can report cloud work even when the tab-label source is `label-cache`: label, naming and consolidation call counts and reported usage determine whether a model ran. Task-mode group counts show the preferred target rather than calling it a hard ceiling. Call counts record dispatched logical batches, including failed requests; preflight failures and shared-result recipients add no new call. A shared result is labelled explicitly, and older records without complete counters do not invent a request count. Schema compatibility retries can make more HTTP requests than logical batches; the provider-usage aggregate counts each HTTP inference request.
- **Provider request usage** is a separate local aggregate for inference and connection-test calls, including those finishing late or in the background. It holds overall and per-provider request counts, reported input/output/total tokens, cached-input and cache-write tokens, reasoning tokens, counts lacking token usage, and returned OpenAI service-tier counts. It stores no titles, URLs, keys, prompts, response bodies or group names. Catalog GETs and incognito calls do not contribute. Settings refreshes when the aggregate changes; **Clear provider usage** resets it independently of cleanup history and grouping memory.
- Provider usage captures its clearing generation before dispatch. A response belonging to an earlier generation is discarded after the usage totals are cleared, while a newly dispatched request records into the new generation. Grouping memory separately stamps labels, name/advice memory, scoped rename preferences, exact results and session plans with a reset generation; work started before **Clear all rules** cannot restore cleared memory.
- **Clear all rules** clears rules, scoped rename preferences, labels, names/advice, exact results and legacy grouping backups, and invalidates earlier session plans. It preserves credentials and behaviour preferences. **Clear run history** removes last-run and history records; **Clear provider usage** resets only the request aggregate. These are separate user controls. Run history is bounded to 20 records.

## Chrome on-device constraint

Foldnex checks for the Prompt API in its Manifest V3 service worker at runtime; historical development observations used Chrome 154. Availability depends on Chrome, device eligibility, policy, disk space and download state. The service worker warms the model when the popup opens, and on startup and install only while background preparation or Auto-group is on; automatic warming requires the setup choice and skips the `immediately` unload setting. A cleanup may wait up to 1.5 seconds for a pending Nano load, reduced by its remaining label reserve, and then uses provisional local placement instead of waiting for the full cold load. Eligible non-incognito provisional tabs are labelled afterwards for a later cleanup. When the Prompt API is absent or unavailable, runs report local fallback rather than claiming on-device inference occurred.

## Performance evidence

Earlier development notes report a prepared Nano window of 118 tabs grouped into ten groups in 0.45 seconds; its first background pass over 106 tabs took about 55 seconds including a roughly 20-second cold load. They also report OpenAI's source-default model at Low effort with Priority labelling and naming 100 tabs in 2.6 seconds, a repeat of about 5 ms, and a default-tier run reaching the 4.5-second budget with half its tabs placed locally. These are historical observations, not current-release benchmarks or timings guaranteed for the visible Chrome tab strip. Model memory and release timings above have the same device-specific limitation. Validate current behaviour and performance in Chrome separately from the deterministic fixtures and mocked provider tests.

## Product principles

- One action creates visible order.
- Preserve user context while removing clutter.

## Acceptance criteria

These are checks for a behaviour change, not a record that the current build passed them.

- Duplicate removal preserves the correct survivor and reports the count.
- Every surviving groupable tab is assigned to a group even when model output is incomplete.
- Pinned, internal, vanished, or newly navigated tabs are handled without destructive assumptions.
- A provider failure keeps successful labels, places any unlabelled tabs locally, and communicates that fallback.
- An unchanged semantic fingerprint set can reuse a result. A fingerprint-changing title or URL change invalidates that result; a single changed tab can reuse labels for unchanged tabs, while ignored query and fragment state does not force fresh classification.
- By site category keeps all Envato pages together, gives YouTube its own group, separates Socials from Email and AI from Code, and makes no provider request.
- A deterministic 200-tab fixture assigns every tab once, produces no more than 30 groups, and repeats the same names and membership on every run.
- By task preserves coherent singleton topics and keeps unplaced tabs in Review Later; it never exceeds ten groups except the documented protection of explicit rules, Socials and remembered user renames.
- A By task cleanup bounds model waiting with the 4.5-second budget and reports how many tabs it placed provisionally. Check total browser latency separately, including duplicate removal, Chrome API application and storage.
- Auto-group files only tabs opened or sent to a new page while it is on, joins the group that already holds their planned group's tabs, never regroups a tab the user took out, and with a cloud engine sends only those tabs.
- The setup card shows until a choice is saved, including for users with **Run from toolbar** on, never blocks a cleanup, and a Cloud choice without a saved key leaves the saved engine active.
- With an on-device engine and both background preparation and Auto-group off, the background labels only the tabs a cleanup just placed by address, and nothing is named or warmed in the background; turning them off drops queued work.
- Idle unloading releases Gemini Nano base sessions after the unload setting and waits for active model work. **Free memory now** and engine switches release the base sessions explicitly; a prompt already running can finish on its own clone, and Chrome determines when memory is freed.
- Last-run diagnostics identify the actual engine, source, token usage, latency, groups, duplicates, fallback class, and quality flags without retaining tab content.
- A cached-label cleanup with a cloud refinement call reports that work. Late and background inference contributes to the separate provider aggregate without storing tab content, and replies started before clearing cannot recreate cleared totals or grouping memory.
- Cloud economy mode is off by default, skips optional cloud refinement when on, and leaves on-device naming and necessary category labelling intact. Priority off sends OpenAI's default tier in cleanups and connection tests.
- API keys must remain outside sync storage, exported rules, logs, and source control. Check the changed paths; this contract does not certify repository history.
- The popup and settings remain usable with keyboard focus, reduced motion, and narrow widths.
- Current ordinary-user browser behavior is checked separately from syntax and mocked-provider checks.
